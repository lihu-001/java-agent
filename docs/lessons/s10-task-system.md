# S10：Task System 持久化任务

本课在独立 s10 子工程中，以 S09 完整源码为起点增加持久化任务图。入口为 `dev.learnagent.s10.TaskMain`，保留五个基础工具、`todo_write`、`task`、`load_skill`、`compact`、三个记忆工具，以及 S03 权限与 S04 Hook。

## 1. 为什么需要任务系统

S05 的 `todo_write` 是本次会话的执行清单：每项只有内容和状态，整表替换，退出即丢。它能提醒“编写接口还没做”，但回答不了两个问题：

- 这个任务现在能不能开始？建表还没完成，接口就不该动手。
- 退出后再来，做到哪了？

S10 把任务变成磁盘上的记录：每个任务有独立 ID、`blockedBy` 前置依赖和 `owner` 认领者，跨会话保留。

| | S05 TodoWrite | S10 Task System |
| --- | --- | --- |
| 存储 | 会话内存 | `.tasks/task_xxxxxxxx.json` |
| 依赖 | 无 | `blockedBy` 依赖图 |
| 生命周期 | 本次会话 | 跨会话 |
| 认领 | 无 | `owner`，claim / complete |
| 更新方式 | 整表替换 | 单条记录的创建、读取、修改 |

两者并存：任务图记录“要交付什么、先后顺序”，`todo_write` 记录“这一个任务我正在走的步骤”。系统提示词里写明分工：几步就能做完、不需要下次继续的事只用 `todo_write`；有依赖或要跨会话继续的才建任务。原因是任务没有删除功能，碎步骤建成任务会一直留在 `.tasks/`，淹没真正要交付的任务；而且每一步都要 create、claim、complete 三次调用，比一次 `todo_write` 贵得多。

## 2. 记录格式

```json
{
  "id": "task_0a1b2c3d",
  "subject": "创建 API 接口",
  "description": "POST /users，校验邮箱",
  "status": "pending",
  "owner": null,
  "blockedBy": ["task_9f8e7d6c"]
}
```

ID 为 `task_` 加 8 位随机十六进制，排他创建，冲突时重试。只允许这六个字段；`pending` 必须没有 owner，`in_progress` / `completed` 必须有。subject 单行 ≤200 字符，description ≤4000 字符，每个任务最多 20 个依赖，最多 200 个任务。

文件是唯一数据源：每次工具调用都重新读取，手动修改立即可见；修改先写临时文件再替换。单个文件无效时 `task_list` 告警跳过，`.tasks` 不存在视为没有任务。

## 3. 两阶段建图

```text
第一批（并行）  task_create(建表) → task_aaaa   task_create(接口) → task_bbbb   task_create(测试) → task_cccc
第二批          task_update(task_bbbb, addBlockedBy=[task_aaaa])
                task_update(task_cccc, addBlockedBy=[task_bbbb])
```

同一条回复里的多个工具调用在任何结果返回前就已确定，`task_create` 无法引用另一个调用刚生成的 ID，所以先建节点、拿到 ID，再加边。`task_update` 先校验整次修改：目标仍为 pending，依赖存在、不是自身、不会成环，全部通过才保存；重复添加不会产生重复边。

## 4. 状态机

```text
pending ──task_claim──→ in_progress ──task_complete──→ completed
```

- `task_claim`：依赖全部 completed 才放行；缺失或损坏的依赖算未完成。
- `task_complete`：只能完成自己认领的任务；结果列出因此刚刚解锁的下游任务。

owner 由程序固定为 `agent`，工具参数里没有 owner，模型不能冒用。S13 Agent Teams 会让多个队友使用不同 owner。

## 5. 不进系统提示词

S09 的记忆索引在启动时进系统提示词；任务不同，状态在一次会话中不断变化，写进系统提示词马上就过时。系统提示词只放规则，模型用 `task_list` 读取当前状态。启动时终端提示 `任务> .tasks 中有 N 个任务，已完成 M 个`，方便用户知道有进度可恢复。

## 6. 与其他机制的关系

| 机制 | 行为 |
| --- | --- |
| S03 权限 | 六个工具直接允许：只读写 `.tasks` 中的记录，不执行命令；真正改代码的工具仍逐次确认 |
| S04 Hook | 六个工具都触发 Pre/PostToolUse，可拦截 |
| S05 TodoWrite | 保留：几步就能完成的小事只用它；做某个任务时，也用它列这个任务内部的步骤 |
| S06 子代理 | 没有任务工具；认领和完成由主代理负责 |
| S08 压缩 | 任务在磁盘上，压缩后用 `task_list` 重新读取；`task_list` 结果可能被微压缩 |
| S09 记忆 | 记忆存“以后仍有用的事实”，任务存“要做的事和进度”，互不替代 |

## 7. 局限

- 顺序执行：同一进程内没有并发认领的锁，多进程同时写同一任务可能互相覆盖；S13 再处理多代理认领。
- 没有删除、取消或重开：清理只能手动删文件。删除被依赖的任务后，下游会一直阻塞。
- 是否完成全靠模型判断，`task_complete` 不验证代码是否真的做完。
- 任务保存在工作目录，换目录就是另一张图。

## 8. 练习

1. 让模型拆三个有依赖的任务，观察第一批并行 `task_create`、第二批 `task_update`。
2. 完成第一个任务后退出，重启说“继续”，确认模型先 `task_list`。
3. 手动把某个任务改成 `completed`，看下游是否显示 `可开始`。
4. 要求模型让测试依赖接口、接口依赖测试，观察环检测报错。
5. 在 `s10/.agents/hook.json` 为 `task_complete` 写一个 PostToolUse 命令，把完成记录追加到日志。

## 9. 验证

自动测试覆盖：目录缺失视为无任务、创建格式与字段顺序、标题与描述校验、依赖去重与整次校验（自身、环、缺失时不保存）、认领需依赖完成、不能重复认领、认领后不能改依赖、只有认领者能完成、完成后返回刚解锁的下游（仍有其他未完成依赖的不算）、新实例从文件恢复与渲染、缺失依赖算未完成、无效文件告警跳过、手动修改即时生效、不留临时文件、ID 校验含路径穿越；六个工具的参数校验与完整生命周期；主循环注册十八个工具、提示词为 S09 加任务规则、第一次会话两阶段建图与阻塞认领、第二次会话 `task_list` 恢复且任务内容不进系统提示词、免确认、Hook 顺序与拦截、子代理无任务工具、启动时报告无效文件。全部使用模拟模型与临时目录。模型是否会主动拆分任务、按依赖推进和跨会话恢复需真实服务单独验收。
