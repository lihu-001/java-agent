# S12：Cron Scheduler 定时计划

本课在独立 s12 子工程中，以 S11 完整源码为起点增加持久化定时计划。入口为 `dev.learnagent.s12.ScheduleMain`，保留 S11 的二十个工具、S03 权限、S04 Hook 与 S11 后台执行器。

## 1. 为什么需要定时计划

S11 的后台任务解决了“启动后立刻返回”，但任务只活在这一次会话的内存里：用户退出，任务取消；用户没有开口，结果也送不回模型。有些事本来就不该由用户坐在终端前触发——每天早上的构建、每小时的健康检查、每周的报表。它们需要的是**记住时间，到点自己执行**。

S12 把计划和执行分开：

```text
模型 ──schedule_create──→ 写入 .schedules/*.json ──→ 立即返回计划 ID
                                      │
                          调度线程每 15 秒检查
                                      │ 到点
                                      ▼
                          BackgroundManager 执行命令
                                      │ 完成
                                      ▼
                          状态与输出写回计划文件
                                      │
                          下一次 schedule_get / schedule_list
```

和 S11 的差别不只是“多个计时器”：计划要跨进程保留，所以必须落盘；程序可能在两次触发之间退出，所以启动时要处理错过的时间；执行发生在没有用户输入的时候，所以权限只能事先确认一次。

## 2. 工具

- `schedule_create(name, cron, command)`：校验五段 cron、名称和命令，创建计划文件并返回 ID 与下一次触发时间。最多 50 个计划。
- `schedule_list()`：列出全部计划，包括启停状态、ID、名称、cron、下一次时间、上次状态与触发次数。
- `schedule_get(id)`：返回计划完整 JSON，包含上次运行状态、结束时间和输出。
- `schedule_pause(id)`：暂停计划，不再触发新的运行；已经开始的命令继续跑完。
- `schedule_resume(id)`：恢复计划，从当前时间重新计算下一次，不补跑暂停期间的时点。
- `schedule_delete(id)`：永久删除计划；正在运行的计划不能删除。

计划保存在工作目录 `.schedules/schedule_xxxxxxxx.json`。文件是唯一数据源，每次操作重新读取，手工修改也会生效；修改经临时文件替换，避免写一半留下坏文件。

## 3. cron 表达式

计划字段用常见的五段 cron：`分 时 日 月 周`，例如 `*/15 * * * *`、`0 9 * * 1-5`。本课不实现解析器：`CronExpression` 把字段解析、范围校验和匹配交给 Hutool 的 `CronPattern`，自己只补两条约定：

- 只接受五段，避免把 Quartz 的秒字段误当成分钟。
- 日与周同时受限时按 Vixie cron 的“或”匹配。Hutool 的单个表达式按“与”处理，所以代码在两者都受限时拆成两个表达式，取较早的下一次。

时间按本机时区解释，最短一分钟。`0 0 31 2 *` 这种永远不存在的日期会在计算下一次时报错，而不是无限回溯。

```java
CronExpression cron = CronExpression.parse("0 9 * * 1-5");
Instant next = cron.next(Instant.now(), ZoneId.systemDefault());
```

## 4. 调度器怎么工作

`ScheduleManager` 只开一个守护线程，按 `scheduler.poll-seconds`（默认 15 秒）轮询：

1. **启动修复**：加载全部计划。上次进程退出时仍为 `running` 的，改为 `cancelled` 并写明原因——否则这个计划会永远显示“运行中”，也无法再次触发。
2. **跳过错过时点**：对启用且 `nextRunAt` 已过期的计划，统计错过的时点数量，把下一次推进到严格晚于当前时间。进程没运行时的时点不补跑，避免一启动就雪崩式执行积压任务。
3. **到点触发**：重新读取计划文件，确认仍启用且到期。若上一次仍是 `running`，只把下一次推进到未来并提示，不增加 `runCount`；否则先在文件中写入 `running`、推进 `nextRunAt`、`runCount` 加一，再调用 `BackgroundManager.start(command, schedule.id())`。先落盘再启动，进程在两者之间崩溃时至少留下可修复的 `running` 记录。
4. **完成回写**：`ScheduleManager` 向 `BackgroundManager` 注册完成监听器。后台任务结束时，只有计划文件仍为 `running` 才写入终态、结束时间和输出；计划已被删除或状态已变化就忽略。输出最多 2000 字符，超出截断并注明。

命令复用 S11 的后台执行器，因此超时仍是 `background.timeout-seconds`，工作目录和输出上限也与 `shell` 相同。

### 定时任务与用户后台任务的区别

| | 用户 `background_run` | 定时计划 |
| --- | --- | --- |
| 是否持久化 | 否，只在内存 | 是，`.schedules/*.json` |
| 每会话总数上限 | 20 | 不占用 |
| 同时运行上限 | 4 | 共享同一个 4 |
| `background_check` | 可见 | 不可见 |
| 结果送达 | `<background-results>` 附加到对话 | 写回计划文件，用 `schedule_get` 查看 |
| 终态记录 | 会话结束即丢弃 | 最多保留 20 条 |

定时任务不进入对话通知，是因为它可能在用户离开后才结束：往历史里塞一条没人会看的通知只会让上下文变长。结果留在文件里，用户回来问“昨天构建成功了吗”，模型用 `schedule_get` 就能回答。

## 5. 与其他机制的关系

| 机制 | 行为 |
| --- | --- |
| S03 权限 | `schedule_create` 与 `shell` 共用硬拒绝规则，其余逐次确认；确认只发生在创建时。`schedule_list` / `schedule_get` / `schedule_pause` 直接允许，`schedule_resume` / `schedule_delete` 逐次确认 |
| S04 Hook | 六个工具都触发 Pre/PostToolUse；真正的定时命令执行发生在无人值守的后台线程中，不再触发 Hook |
| S05 TodoWrite | 创建计划是一次普通工具调用，不影响清单提醒计数 |
| S06 子代理 | 没有定时工具：子代理结束即丢弃，留下的计划没有归属 |
| S08 压缩 | 定时结果不进入对话历史，不参与微压缩或总结 |
| S09 记忆 | 长期偏好仍写记忆；计划本身是结构化文件，不写记忆 |
| S10 任务图 | 可以让定时计划负责定时触发，任务图负责跨会话的工作项状态 |
| S11 后台任务 | 定时命令复用同一个执行器和同时运行上限 |

`ChatLoop` 本课不修改：调度线程与对话循环通过计划文件和后台执行器解耦，不需要在请求模型前插入额外步骤。

## 6. 局限

- **只在进程运行时触发**。它不是操作系统计划任务；程序退出后不会执行，需要常驻时应由外部服务托管进程或改用系统计划任务。
- **错过的时点不补跑**。只报告数量并推进到未来，避免重启后集中执行大量过期任务。
- **创建后无人值守**。确认只发生在创建时，之后每次触发都直接执行；只应调度愿意让它自行运行的命令。
- **重叠时跳过**。同一计划上一次未结束时，本次时点被跳过，不会并发堆积。
- **结果不主动通知**。用户离开期间完成的结果只写文件，不会唤醒模型，也不会出现在下一次对话中。
- **不是沙箱**。命令以当前用户权限运行，与 `shell` 相同。
- **单进程假设**。两个 Agent 进程同时打开同一个工作目录时，没有跨进程锁，可能重复触发同一计划。

## 7. 练习

1. 让模型创建 `* * * * *` 的计划执行 `echo tick`，保持程序运行两分钟，观察终端触发日志。
2. 用 `schedule_get` 查看 `lastStatus`、`lastFinishedAt` 和输出；再 `schedule_list` 对比渲染格式。
3. 创建 `0 9 * * 1-5` 的工作日计划，确认返回的下一次时间落在工作日 9:00。
4. 暂停计划，等到原定时间确认没有触发；恢复后确认下一次从当前时间重新计算。
5. 退出程序，几分钟后重新启动，观察终端报告的错过时点数，确认计划没有被补跑。
6. 手工把计划文件的 `lastStatus` 改成 `running` 后重启，确认启动修复为 `cancelled`。
7. 创建一个执行 `Start-Sleep 90; Write-Output done` 的每分钟计划，观察第二次到点时因上一次仍在运行而跳过。
