# S08：Context Compact 上下文压缩

本课在独立 s08 子工程中，以 S07 完整源码为起点增加上下文压缩。入口为 `dev.learnagent.s08.CompactMain`，保留五个基础工具、`todo_write`、`task`、`load_skill`，以及 S03 权限与 S04 Hook。

## 1. 为什么要压缩

每次请求模型都要发送完整历史。读几个大文件、跑几次命令后，历史会迅速变长：请求变慢、费用变高，最终超过模型的上下文窗口而失败。工具结果往往是大头，而且大多只在当时有用，读完的文件内容在几步之后就很少再需要原文。

本课分三层处理，代价从低到高：

```text
每次请求前
  ├─ 1. 微压缩：较早的长工具结果 → “[已压缩] 较早的 read_file 工具结果（原 N 字符）……”
  │            不请求模型，只改本次发送的内容，内存历史仍是原文
  ├─ 2. 自动压缩：对话仍超过阈值 → 保存完整记录 → 请模型总结 → 历史 = 系统提示词 + 摘要
  └─ 3. 手动压缩：模型上一批调用了 compact → 同样的总结（不看阈值）
```

## 2. 微压缩

`MicroCompact.apply(messages, keep)` 从后往前保留最近 `keep` 个工具结果的原文，更早且超过 200 字符的换成一行占位说明，`tool_call_id` 与消息顺序不变，协议依然合法。以下工具的结果不替换：`task`（子代理总结，重新获取需要重跑子任务）、`load_skill`（模型正按它执行）、`todo_write` 与 `compact`（结果很短，也不应重复调用）。

微压缩只作用于发给模型的那份请求，内存中的历史仍保留原文。这样自动压缩时能把原文写进完整记录；代价是每次请求都要重新计算一遍，这对教学规模的历史可以忽略。

## 3. 自动压缩

微压缩后，若对话（不含系统提示词）的粗略字符数超过 `compact.threshold-chars`，`ContextCompactor` 依次：

1. 把内存历史原文写成 `工作目录/.transcripts/transcript-时间.jsonl`，每行一条消息；写入失败就不总结，否则被替换的内容将无从找回。
2. 用独立的总结提示词请求模型，不带工具；输入是渲染后的对话文本，超过 60000 字符时只保留最近部分。
3. 用一条 user 消息代替全部历史：

```text
[对话已压缩] 之前的对话已被总结，完整记录保存在工作目录的 .transcripts/transcript-….jsonl（JSONL），需要原文细节时可用 read_file 读取。

摘要：
……模型写的摘要（最多 8000 字符）……

程序保存的当前状态（不是摘要，以此为准）：
任务清单（1/3 完成）：……

用户最新输入（原文）：
……
```

关键约定：

- 系统提示词原样保留，不计入阈值：它无法被压缩，计入的话阈值较小时会在每次摘要后反复压缩。
- 最近一条真实用户输入原样附在最后，不交给模型改写，避免总结时丢失或曲解当前要求。
- 任务清单由程序保存，直接附加原文，不依赖模型复述。
- 总结请求不计入 `agent.max-model-calls`，不经过 Hook，也不触发 Stop。
- 总结失败（请求失败、空回复、返回工具调用）时打印告警，继续用未总结的上下文请求，不丢弃历史。
- 压缩可能发生在一轮工具调用的中途。此时摘要成为新的本轮起点：之后的工具调用仍正常补齐，Stop 只收到摘要之后的消息。

## 4. 手动压缩：compact 工具

```text
assistant → compact({"focus":"保留修改过的文件路径"})  + 同批的 read_file
tool      → 已安排压缩：下一次模型请求前……
tool      → read_file 的结果
（下一次请求前执行总结；focus 追加到总结提示词）
```

`compact` 只登记请求。若在执行工具时立即替换历史，同一批中其他工具调用的结果就没有对应的 assistant 消息，协议会被破坏。因此等整批结果补齐、下一次请求前才执行。`focus` 可选，最多 200 字符。

`compact` 免逐次确认，仍经过 PreToolUse/PostToolUse，Hook 可以拦截。

## 5. 与其他机制的关系

| 机制 | 行为 |
| --- | --- |
| S03 权限 | `compact` 直接允许；完整记录由程序写入，不经过 `write_file` 审批 |
| S04 Hook | `compact` 触发 Pre/PostToolUse；总结请求不是工具调用，不触发 Hook |
| S05 清单 | 清单不在压缩范围内，摘要后附加程序保存的原文 |
| S06 子代理 | 子代理历史每次 `task` 新建，结束即丢弃，不压缩，也没有 `compact`；主代理中的 `task` 结果不做微压缩 |
| S07 技能 | 技能目录在系统提示词里，压缩后仍在；`load_skill` 结果不做微压缩，被总结后可再次加载 |

## 6. 配置

| 配置项 | 含义 | 默认值 |
| --- | --- | --- |
| `compact.threshold-chars` | 对话粗略字符数超过此值时自动总结 | `50000` |
| `compact.keep-tool-results` | 微压缩保留原文的最近工具结果数 | `3` |

字符数只是粗略估算：中文一个字符大约对应一个 token，英文与代码约 3—4 个字符对应一个 token。正式实现应使用服务商返回的 usage 或分词器计数。

## 7. 局限

- 摘要会丢失细节，模型可能遗漏关键约束；完整记录可以找回原文，但需要模型主动读取。
- `.transcripts/` 保存原始对话和工具结果，可能包含敏感内容，不会自动清理；仓库 `.gitignore` 已忽略 `.transcripts/`。
- 单条消息本身超过上下文窗口（例如一次超长工具结果）不在本课处理范围，仍依赖各工具的输出上限。
- 没有提供用户侧命令触发压缩，也不支持从记录恢复会话。

## 8. 练习

1. 设置 `compact.threshold-chars=3000`，让模型连续读取几个文件，观察 `压缩> 微压缩` 与 `压缩> 完成` 输出，然后打开 `.transcripts/` 下的记录。
2. 压缩后提问之前读过的某个文件细节，观察模型是重新读取文件、读取记录还是凭摘要回答。
3. 输入：“先列出任务清单，然后压缩上下文，再继续。”确认清单在摘要后仍完整。
4. 在 `s08/.agents/hook.json` 为 `compact` 写一个 PreToolUse 拒绝规则，观察模型被拒后的反应。

## 9. 验证

自动测试覆盖：微压缩只替换较早的长结果、保持调用 ID 与顺序、不修改入参、跳过豁免工具；阈值以下只微压缩且内存历史保留原文；超过阈值时保存完整 JSONL、总结请求不带工具、摘要附加任务清单与最新用户输入；`compact` 登记只生效一次并传递 focus，参数校验失败不登记；总结失败、返回工具调用、记录无法保存时保留历史；没有可总结内容时跳过；再次压缩时旧摘要参与总结；一轮工具调用中途压缩后协议仍合法、下一轮基于摘要继续；总结请求不计入调用上限；`compact` 免确认、经过 Hook、可被 Hook 拦截。全部使用模拟模型与临时目录。真实模型的摘要质量和压缩后是否能继续任务，需要真实服务单独验收。
